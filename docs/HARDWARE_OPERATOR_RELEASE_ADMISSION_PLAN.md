## 1. Decision: implement a small local release controller; do not deploy a full TUF service

The missing component is **not** another parser, mock test or new keypair. It is a **separate, trusted hardware release-admission decision** between a frozen canonical ZIP and the existing `deus-run` execution domain. Build/provenance verification, owner authorization and one-shot device access are independent security decisions.

**Selected design:** canonical `bundle_guard.py build/validate` for the eventual complete reviewed source; a **detached**, time-limited Ed25519 SSHSIG owner approval over a canonical JSON release statement containing the **final ZIP SHA-256**; a locally trusted, non-ChatGPT **release controller** on owner Windows that verifies all bindings and durably consumes a one-time nonce before any potentially mutating child; then a reviewed single Windows result owner with real PASS/FAIL evidence. Owner keys remain in their existing restricted storage, not DEUS MCP, Git, bundle, evidence, or GitHub Actions secrets. New approval uses the existing independently trusted owner **public** key; no rotation just to unblock.

**Recommended deployment choice:** local owner-controlled Windows admission, not an arbitrary GitHub Actions job or GitHub self-hosted runner with access to USB and signing secrets. GitHub remains useful for source review, static/CI build checks and non-secret provenance; its environment approvals do not themselves attest local `usb:001:8` and do not substitute for exact signed owner consent.

**Explicitly rejected:** signing a ZIP digest before the ZIP exists; embedding a signature of the ZIP’s whole hash in that same ZIP (circular dependency); conflating source-lock, build provenance, signature and device authorization; treating `bundle_guard build/validate` as `release`; modifying an expired signature’s timestamp; replaying a consumed nonce; executing the old quarantined stage; manually ZIPing, relabeling, wrapping or rerouting an earlier client-layer denied hardware generator.

| Boundary | Implementation / source of trust | Fail-closed decision |
|---|---|---|
| Source and test identity | Exact reviewed Git tree/commit **plus** pinned WIP files and hashes until a commit is separately authorized; existing source-only v2 SHA inventory is **unsigned** | Reject any unapproved byte drift; reuse already accepted unchanged Host 168/168, v2 Windows 6/6 and Linux 12/12 tests |
| Build / canonical archive | One reviewed physical Windows `apply.ps1` (not yet authored), source-locked payload, one `bundle_spec.json`; canonical `bundle_guard build` + independent `validate`; whole ZIP SHA256 and member index | Reject unsafe paths, duplicate entries, extra result writer, quarantine, unexpected binary/secret or package ID |
| Nonsecret build provenance | Offline record of source hashes, tool versions, build inputs, commands, build outputs, ZIP hash, builder identity and native qualification receipt; SLSA/in-toto concepts without claiming formal certified SLSA level | Reject if provenance is incomplete, self-issued by untrusted source, or mismatches exact ZIP |
| Owner consent | Detached canonical JSON + owner Ed25519 SSHSIG under pinned **namespace**, previously enrolled trusted signer identity and independent trust anchor | Reject unknown key, namespace, signature, expired/future approval, changed ZIP, source, package ID, port or operation set |
| Trusted release controller | **To be implemented and natively qualified** separate from chat/MCP and unsigned bundle; Windows owner-local control independent of ZIP contents | Verify all predicates **before** launch. A project document or GitHub approval cannot grant the release permission |
| One-time hardware permission | Exact target port `usb:001:8`; preflight runtime `1209:000C`, installed rev5 source pin; bounded single ENTER and INFO; atomic off-Git nonce consumption before uncertain start boundary | Reject replay, prior consumption, incompatible endpoint, source/firmware capability drift, ambiguous preconditions |
| Result/evidence ownership | One top-level `apply.ps1` writes one `DEUS_OS_RUNNER_RESULT_V1`, one original native indexed `Evidence/*.evidence.zip` on PASS or classified FAIL | After possible ENTER, SSH timeout/receipt loss `RESET_POSSIBLY_ATTEMPTED`; no retry; evidence-sealing failure cannot yield PASS |
| Human physical GO | Fresh explicit owner's bench-specific consent after review of verified package and recovery/USB preconditions | Lack of GO or client/tool denial => `RELEASE_STOP`; no implicit GO from key possession or a prior PASS |

A trust boundary can be **the same human owner** but cannot be a second trust claim derived only from inside the artifact being approved. Store the public trust anchor outside the candidate source/bundle, and never let the runner select its own trusted key.

## 3. Release statement contract (separate sidecar; never embedded in signed ZIP)

**Design proposal — new schema, not yet implemented:** `DEUS_OS_HARDWARE_RELEASE_APPROVAL_V1`. Canonical deterministic UTF-8 JSON with **unique exact fields**, upper-case SHA256 format, strict field types, and a detached OpenSSH Ed25519 SSHSIG. Pin a **new** namespace such as `deus-os-hardware-release-v1` after deliberate owner review (do not silently inherit the old namespace or reinterpret the previous v1 consent).

Fields that must be signed together:

- `schema`, `workflow_id`, `package_id`, `bundle_schema`, `operator_profile=HARDWARE_MUTATING`;
- `operator_zip_sha256` and exact byte size, plus full `source_lock_sha256`, source Git tree identity, build provenance record SHA, and exact runner/entrypoint SHA;
- `owner_identity`, trusted signing namespace, `valid_from_utc`, `valid_until_utc` (bounded approval window), `nonce` (unique unpredictable 128-bit-or-more token);
- `host_identity` and physical-port identity `usb:001:8`, required old runtime `1209:000C` with exact source-tree pin `ccbd50200ec7f0ec53da6b1048d7377271dfb7bd`, target bootloader `1209:000D`;
- exact allowed operations: **one** reset/ENTER; up to one new `000D` node ownership adjustment `deus:0600` after approved preflight; **one** read-only INFO; `flash_allowed=false`, `erase_allowed=false`, `retry_allowed=false`, `automatic_return=false`;
- references (SHA only, never raw secret/device dumps) to required recovery readiness and latest native acceptance proof.

A statement signed **before** canonical ZIP finalization is invalid for release. The issuance order is **finalize ZIP → compute ZIP SHA → generate canonical sidecar approval → owner signs that sidecar → independent verifier reopens exact ZIP and checks sidecar+signature**. Do not include either approval or signature in the ZIP being hashed, unless a formally designed different hash domain is used.

## 4. State machine and result contract

`SOURCE_DRAFT → SOURCE_REVIEWED → NATIVE_QUALIFIED → ZIP_VALIDATED → OWNER_SIGNED → RELEASE_ADMITTED → NONCE_CONSUMED → ONE_ATTEMPT_ENTERED → INFO_OBSERVED / STOP_AMBIGUOUS / STOP_FAILED → ORIGINAL_EVIDENCE_SEALED`.

No transition may skip a state or promote a synthetic receipt to physical proof. Each transition records exact bytes, origin, timestamp and tool identity in bounded nonsecret evidence. Invalid source/signature/time/nonce/physical identity is `RELEASE_STOP` **before** child start.

1. **Offline preparation:** finish and independently review a single real hardware `apply.ps1` with one `DEUS_RUN_RESULT_PATH` writer; lock source; run only source-changed native AST/positive and failure-injection tests; seal original native PASS/FAIL qualification evidence.
2. **Canonical archive:** build and validate once by the canonical builder, freeze whole ZIP digest and source set. Never delete quarantine from the old v1 stage or treat a source-only directory as a releasable stage.
3. **Owner signature:** verify existing independent signer public-key enrolment and owner-local signing capability without reading/exporting private bytes. Obtain fresh short-lived exact ZIP-bound approval after reviewing bench preconditions. Verify detached signature and expiry in the trusted release controller.
4. **Trusted admission:** verify ZIP+source hashes, scope, signature, non-replay nonce, native proof, configured physical port, source/runtime identity and tools; produce signed or integrity-protected `RELEASE_ADMITTED` receipt tied to ZIP+nonce. **Do not call generic `bundle_guard release` a hardware permit**; it correctly denies `HARDWARE_MUTATING`.
5. **Durable consumption:** immediately **before** the point where remote execution may become mutating, atomically create+fsync a consumed nonce record in a pre-provisioned restricted off-Git store. If uncertain whether consumption/child start happened, **STOP with no retry**. Never delete a consumed record as a recovery workaround.
6. **Exact operator:** only the individually admitted single-run hardware path may perform the one ENTER/one read-only INFO. Bound the installed Windows runner's result gate to the manifest `package_id`. Capture original raw child `result.json`, not a normalized or reserialized replacement. Do not count a post-ENTER SSH loss as zero reset.
7. **Original evidence:** one locally retained `Evidence/*.evidence.zip` with member hashes, whole SHA, nonsecret bounded native command results, source/ZIP/admission identity and poststate, including FAIL. The installed runner validates the original evidence; only a physically confirmed INFO yields `GATE3_000D_SCOPED_PHYSICAL_ONE_RESET_ONE_INFO_PASS`. `FULL_GATE3` remains separate until other open recovery-route predicates are independently accepted.

**Integration choice still to make/qualify:** the trusted admission may be enforced by extending the installed `deus-run` **only after** native source/test/rollback acceptance, or by an independently protected local execution controller that gates `deus-run` itself; an untrusted self-authorizing script inside the ZIP is insufficient. No such controller has been implemented yet. Do not suggest running a manual SSH/USB command in place of the approved runner.

**Sequencing:** RA-01–03 are safe design/verification-only preparations, but **do not** create a physical execution capability. RA-04/07 need a permitted and independently approved hardware-executable authoring/integration environment; historical client-layer `BLOCKED` calls cannot be worked around via generic DEUS file/process tools. RA-06 signing requires the owner to act in their local protected key domain; key continuity is supported by previous Ed25519 verification but signer accessibility is **not** proven from DEUS MCP.

**Definition of release-admission specification closure:** the optional hardware-execution policy is independently reviewed. **Definition of release-controller implementation closure:** RA-01–07 native qualification plus trusted controller. **Definition of one physical session closure:** separate owner GO and RA-08 real hardware evidence. **Definition of original Gate-3 closure:** governed exclusively by the current migration acceptance checklist — independently accepted non-destructive exact-source signed-v6/signed-v7 G3-4b recovery-route readiness attestation. Neither this controller, RA-08 nor any actual physical recovery drill may be silently added as new mandatory Gate-3 predicates.

## 6. External engineering basis and scope limitations

- [NIST SP 800-218 (SSDF)](https://csrc.nist.gov/pubs/sp/800/218/final): source integrity, security checks and protected release lifecycle. **Guidance, not formal Deus OS certification.**
- [NIST CSWP 5, Security Considerations for Code Signing](https://csrc.nist.gov/pubs/cswp/5/security-considerations-for-code-signing/final): signing authenticates origin and integrity, not device-level fitness or blanket permission.
- [NIST SP 800-193, Platform Firmware Resiliency](https://csrc.nist.gov/pubs/sp/800/193/final): protection, detection and recovery principles (relevant to emergency bootloader route).
- [SLSA v1.2 provenance and artifact verification](https://slsa.dev/spec/v1.2/verifying-artifacts): provenance must be checked against **expected** builder/source/build parameters and exact subject digest; a self-declared JSON does not create trust.
- [in-toto supply-chain steps/layout](https://in-toto.io/docs/getting-started/): signed functionary/step accountability and material/product chain; adapt **concepts**, not the full framework for one bench.
- [OpenSSH ssh-keygen ALLOWED SIGNERS](https://man.openbsd.org/cgi-bin/man.cgi/OpenBSD-current/man1/ssh-keygen): pinned principal and namespace, detached signature verification.
- [TUF metadata](https://theupdateframework.io/docs/metadata/): separation of roles, expiry, snapshot consistency and rollback protection. **Use short-lived consent and anti-replay principles; do not claim full TUF deployment.**
- [GitHub Actions environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) and [self-hosted runner security](https://docs.github.com/en/actions/reference/security/secure-use): useful CI approval model but local bench, signing key and USB secrets must not depend on untrusted self-hosted workflows.
