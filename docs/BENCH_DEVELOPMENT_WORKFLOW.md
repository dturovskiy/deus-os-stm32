## What we do for each firmware change

`edit → build → relevant tests → inspect target/package → one update → smoke test`.

**Scope is BENCH, not formal Gate4 acceptance.** No new RA stage, approval service, signer plugin, controller installation, Python dependency bundle or broad regression campaign is required for ordinary development. Reuse the tools already present. Prior accepted tests/metadata are not rerun without changed inputs. A new test/tool must answer a **specific unresolved failure or compatibility question** directly related to this board.

**Definition of done for a bench change:** firmware built and relevant unit tests pass; exact candidate/target checked; actual physical update and focused smoke test observed; one short log records image SHA, device identification, bootloader INFO/version policy, transfer/commit result, post-boot behavior and errors. If the hardware host is unavailable, report **BLOCKED BY DEVICE ACCESS**, not a synthetic substitute or an additional paperwork Gate. Debug the actual blocking layer first.

Keep production/distribution governance plans deferred, not deleted. Do not conflate bench observations with formal Gate4 claims. Normal work may still require explicit board-operation authorization and must respect actual transport/firmware safety constraints.

## First test of the current signed v6

1. Use the **already implemented** `DeusDeviceClient.EnterBootloaderAsync` and `FirmwareUpdateClient.InfoAsync/UpdateAsync`, not a new protocol. Windows holds ST-LINK/UART; Ubuntu holds native USB in the last verified topology. Discover the live device/port, do not reuse historical bus numbers.
2. Take a concise prestate: device identity, current `000C` app state, bootloader version floor and expected target/transport. Stop on mismatch. A one-time ENTER causes reset and must not be blindly repeated on a missing reply.
3. On the actual `000D` bootloader, inspect `INFO`; confirm normal v6 eligibility (`version > authenticated floor` with a valid current app).
4. When explicitly approved for this board action, perform **one** signed v6 update through the existing bootloader `BEGIN → AUTHORIZE_HEADER → DATA → END` contract. Preserve commit response and post-install identity.
5. After reboot check `1209:000E` single Management IF0, basic RPC, UART, OLED, scheduler, IWDG and current resource diagnostics. Record the result in **one log**. Do not automatically run destructive failure/rollback campaigns in the same session.

**Important practical distinction:** bare ST-LINK application programming at `0x08002000` is not an equivalent replacement for the bootloader signed-package workflow. The bootloader has authenticated version metadata in pages 60/61. A raw application write can leave those records inconsistent. ST-LINK is the recovery/debug tool, not the default way to install this pre-signed `000E` candidate.
