## 0. Owner's reference case: XD OS / 19,456-byte compressed PC operating system — 2026-11-08

Owner video: https://www.youtube.com/watch?v=Xzv7CS0Fvnw ("I Built a 19 KB Operating System from Scratch", CodingWalaXD, 2026-11-07). Actual open-tab YouTube description and chapter labels checked, plus primary author GitHub repository https://github.com/eklavya-raj/xdos read through live GitHub connector. This corrects prior framing implying it must be a trivial 19KB scheduler. The author really supplies x86 assembly code implementing desktop windows, terminal, notepad, paint, calculator, file manager, games, RTL8139 NIC, TCP/IP, TLS 1.3 and a simple browser. No frame-by-frame playback or complete video transcript was available; do not claim direct runtime reproduction.

- In include/defs.inc: IMGSEC equ 38, 38 * 512 = 19,456 bytes. This is a FULL BOOTABLE COMPRESSED x86 disk image, NOT uncompressed runtime code size. tools/build.py NASM-compiles raw out/kernel.bin, filters relative x86 branches, applies adaptive entropy compressor in tools/pack.py, embeds compressed payload into boot/boot.asm, which unpacks code into RAM.
- Exact source compression-memory distinction: tools/pack.py HBITS=22 and tab=bytearray(2<<HBITS) = 8,388,608 bytes (8 MiB); boot/boot.asm clears 1<<21 32-bit words in its CMTAB scratch region, also 8 MiB. README/Makefile runs QEMU with -m 64 (64 MiB RAM). By contrast STM32F103C8 has 20 KiB SRAM, and compiled normal app executes in place from Flash. It cannot replicate the same 8 MiB whole-kernel RAM decompression method. Small bounded on-demand literal/asset decompression is a separate valid candidate.
- boot/boot.asm relies on PC BIOS int 0x13 disk loads, int 0x10 VGA/VBE mode and BIOS-provided font; other included PC services differ from STM32. Browser source kernel/apps/browser.inc says no css, no images, i.e. real but intentionally minimal HTML browser. kernel/net/tls.inc says tls 1.3,chacha20-poly1305 + x25519 only. no cert checks; README explicitly says HTTPS does not verify server certificates and terminal curl requires -k. NOT equivalent to authenticated production HTTPS.
- Video description/chapters include 512-byte boot, desktop fonts, browser, Flappy/Hill Climb boot-sector games, size reduction, windows/menu and networking/curl. Actual code and README support those features; screenshots/tests in tools/test_all.py exist, but were not executed by this audit.
- STM32 numbers: installed signed normal v8 native uncompressed os.bin 53,196 B; last unsigned source-only ESP Bridge candidate native uncompressed os.bin 52,372 B; accepted application ceiling 53,248 B. These are not equivalent metrics to XDOS compressed 19,456-byte disk image. Size density is strong evidence of engineering efficiency, NOT on its own proof of CPU performance, RAM footprint, authenticated TLS, fault isolation, USB or firmware rollback.
- Reusable engineering ideas: Assembly-level data layout and specialized encodings, shared UI/status text functions, deduplicated constant strings/tables, selective low-RAM decompression of literal tables/assets; move ESP ROM image and networking/TCP/IP complexity to host/ESP. Apply with source-locked ARM before/after proofs, retaining STM32 USB Management, watchdog, recovery, signed bootloader, OLED and Node Link. Do not blindly port x86 assembly to ARM Thumb-2 or claim 19KB as demonstrated attainable target for this OS.

## A. Exact boundaries / what the numbers mean

- MCU memory is not all available to the normal application. `linker/stm32f103c8.ld`: bootloader occupies `0x08000000..0x08001FFF` (8 KiB); app `FLASH ORIGIN=0x08002000, LENGTH=52K`, ending at `0x0800F000` (53,248 bytes); metadata and persistence slots `0x0800F000..0x0800FFFF` (4 KiB) must remain untouched. No suggestion to bypass application acceptance ceiling or reclaim reserved pages.
- **Installed signed normal v8:** 53,196 /53,248 Flash = 52 B headroom, SRAM 8,468 /11,264 B static. These installed-version numbers are distinct from the next candidates.
- **Source-only Windows native ARM resource proofs:** scheduler diagnostics `-Os` 52,924 Flash (324 spare); scheduler plus four UI components `-Os` 51,468 (1,780 spare), delta **−1,728 B** versus installed v8; source-integrated USB↔USART2 ESP maintenance bridge v0 52,372 (876 spare), delta **+904 B** versus optimized UI, SRAM 8,480/11,264. These candidates are **unsigned / NOT INSTALLED** and their binary-specific runtime on the physical STM32 is not tested. Source evidence: `docs/ESP01_FLASH_BRIDGE_MAINTENANCE_V0_DESIGN.md` §0a and §1; original Windows arm-test Evidence hashes documented there.
- `scripts/build_firmware.ps1` uses `-ffunction-sections -fdata-sections -Wl,--gc-sections`, hybrid per-source `-Os` and `-O2`, but **no `-flto`**, and exact closed list of **36 source C files**, which must stay aligned. Flags/resource changes require new source-pinned offline Windows ARM native measurement; a source-text line count cannot prove Flash bytes.

**Measured previously and accepted**: `scheduler_diagnostics.c -O2→-Os` saved 272 B; adding a four-UI-source `-Os` profile saved 1,456 B more; total 1,728 B. This code selection is already in the current source candidate. Do **not** repeat identical experiment or treat old savings as an additional opportunity.

**Next compiler-only A/B candidates, not measured yet:** `command_service.c`, `binary_rpc.c`, `application_runtime_bridge.c`, `oled_ui_layout.c`, and perhaps `ssd1306.c`, each one-at-a-time/atomic same-source Windows ARM native image diff. Do NOT start by changing `usb_device.c`, `iwdg.c` or `binary_frame.c` without a timing/USB/reset/CRC regression plan. `-flto` is absent and is a separate optional opt-in experiment, not a proven gain; it can change inlining, layout, stack use and timing.

## D. Engineering decision and next owner workflow

1. **Priority 1 (no functional regression):** address `console_execute_safe_method` (5,368B) and the human-readable repetitive string/report layer, centralize formatting/compact read-only metrics, avoid duplicating text between OLED/USB/USART; preserve current RPC/wire/CLI data ABI and commands. Move **presentation formatting** to Mac mini where feasible, keeping STM32 fault/health status enough to debug USB failure.
2. **Priority 2 (BENCH/NORMAL profile split):** remove *active intrusive self-tests and their command registrations* from normal image **only behind an explicit build profile**, while retaining all runtime health, watchdog, fault recovery, stack guards, startup and update paths. Keep full BENCH profile for regression and rescue. Measure each delta from a common source baseline, mark the feature difference honestly (not equivalent full-feature firmware).
3. **Priority 3:** use the existing source-only bridge approach: keep ESP ROM SLIP, binary verification, image handling, retries and larger buffers **on the Mac mini**, and only a bounded USB↔USART2 proxy and ESP boot control on STM32. Do not copy ESP image/esptool/OTA/TCP/IP into STM32 Flash. Wi-Fi TCP/IP stays on ESP.
4. **Priority 4:** one new native Windows ARM `os.bin`/ELF/MAP profile compare **only after a changed candidate exists**; derive attributed before/after by object/section in MAP and `nm -S --size-sort`, including 4-byte app alignment, Flash ceiling, SRAM, stack-usage, IRQ timing and USB continuity. Offline O0/Os/UBSan host tests and Native Windows build are separate proofs. No auto flashing or signing.
5. Accept output only if it preserves node HELLO/CRC32, Management USB framing, firmware update/rollback, flash persistence and OLED normal mode. Define a *measured* Flash margin for ESP control + Wi-Fi protocol rather than assert a guessed 19,000B size. The oft-cited 19KB systems may have fundamentally different selected modules/peripheral stacks; no specific comparable product/equivalent feature set was supplied.
