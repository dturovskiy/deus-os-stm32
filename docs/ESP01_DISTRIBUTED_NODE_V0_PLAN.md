## Goal

Prove **one real remote computation on one ESP-01**, orchestrated by the installed Deus OS STM32F103C8 without replacing the accepted local application/runtime, USB Management, watchdog, OLED, or signed-v6 bootloader. The endpoint behaves as a separate MCU/node, not an extra SRAM bank or a transparent second scheduler. Future ESP32/other MCU nodes should require a new transport/backend and module implementation, not a rewrite of the system/application semantics.

Current accepted design `OS_APPLICATION_AND_UI_MODEL_PLAN.md` §13 describes ESP as a network coprocessor with STM32 as authoritative device runtime. This v0 proposes a **broader optional compute-node role** and must not be mistaken for an already accepted networking implementation. `NETWORK` OLED indicator remains OFF until there is an actually online network service; mere UART presence does not turn it on.

## Scope and ownership

- **STM32, node 0:** authoritative local kernel, scheduler, system health, USB/RPC endpoint, status bar, IWDG, existing `system.home`/`device.info`; controller for subordinate work.
- **ESP-01 / ESP8266, node 1:** own CPU, RAM, SPI flash and firmware, independent work queue and heartbeat; initially only a deterministic offloaded job (for example CRC32 of up to 16 input bytes), not TCP/IP or user-facing network management.
- **Physical transport:** proposed STM32 USART2 default PA2 TX -> ESP U0RXD; PA3 RX <- ESP U0TXD; common GND, stable **separate 3.3 V supply**, 3.3 V logic only. Preserve PA9/PA10 USART1/Windows CH340 diagnostics, PA11/PA12 Ubuntu-owned target USB/VBUS, PB6/PB7 OLED I2C1, PC13 LED and PA13/PA14 SWD. Source scan on 2026-10-31 found no USART2 driver or current PA2/PA3 owner; board-specific physical accessibility and cable/pin occupancy **NOT YET VERIFIED**.
- **ESP module controls:** EN/CH_PD must permit operation, RST high in normal operation, GPIO0 high for normal boot / low at reset only for deliberate UART bootloading, GPIO2 must meet boot-strapping requirements. Use a reliable 3.3 V source sized for Wi-Fi current bursts (Espressif recommends ~500 mA supply capacity). Exact ESP-01 revision/flash size, boot strap pullups, regulator and pin labels require owner-side identification **before power or wiring**; never assume Blue Pill, ST-LINK or CH340 3.3 V output safely supplies the ESP.
- **No hotplug claim:** connect/disconnect only with device power off until the electrical interface is explicitly designed for hot insertion.

If a working AT image is present, optional isolated `AT` / `AT+GMR` probing may establish link and module health, but **AT-only is not remote job execution**.
2. **Host/offline protocol prototype:** define bounded serial frames and a deterministic node-1 emulator/test, including malformed length/CRC, duplicate/out-of-order sequence, timeout, lost node, version mismatch and hot-return behavior. No firmware or target update.
3. **ESP node-runtime v0:** minimum application on ESP8266 accepts `HELLO`, `PING`, `JOB_CRC32`, `GET_STATUS` and returns typed results. It owns its own program, scheduler/loop and memory. Verify locally first with approved ESP programming path; this is a separate **explicit ESP write**.
4. **STM32 USART2 v0 + bridge:** small bounded RX ring/parser and single request-in-flight controller, no dynamic heap, no new generic scheduler. Negotiate protocol version and node-1 capabilities; queue job asynchronously and report result through a **scoped** diagnostic path; preserve existing USART1 debug and USB behavior. Fit linked 52-KiB application maximum and SRAM/stack budgets; last observed source-sync image used Flash **48,992/53,248** and SRAM **7,516/11,264** (headrooms 4,256 / 3,748). These are historical measurements, not a guarantee that this new feature fits. Separate owner GO and signed-candidate/recovery preflight before **any STM32 Flash/update**.
5. **Physical one-node acceptance, BENCH only:** one real HELLO (expected node=1, compatible protocol), one real job processed by ESP rather than STM, matched result/sequence; repeated jobs no leak; ESP absent/restarted yields bounded timeout and STM USB info/ping/health, watchdog and OLED stay alive; reconnect returns READY. No network indicator until Wi-Fi path is separately implemented.

## Proposed wire contract — DRAFT, not frozen

Dedicated UART2 8N1; initial baud selected only after ESP bring-up (e.g. 115200 if stable). Explicit bounded frame, version, message type, node ID, sequence/request ID, payload length, CRC-16, no arbitrary pointers, no native STM RPC IDs reused blindly. One outstanding job in v0, at most 16 request payload bytes in the first job. Maximum raw frame and endianness frozen **before implementation** and covered by common host/source tests; no fake "generic" API yet. Strict timeout (no infinite wait), bounded retry only for idempotent reads, safe duplicate handling, exact node/sequence match and fail-closed unsupported message handling.

Initial node states: `ABSENT -> PROBING -> READY -> BUSY`, and `DEGRADED/ABSENT` after silence or invalid handshake. ESP's failure must never block local STM IWDG feeding, USB management, or normal OLED. No remote execution of arbitrary code, no remote Flash/erase, no network exposure of unauthenticated USB RPC, no remote STM reset, no shared-memory promise. Flash/provisioning and Wi-Fi credentials/security are separate future scoped contracts.

## Practical first outcome / stop conditions

The **first milestone** is not Wi-Fi: **STM32 -> USART2 -> ESP-01 executes bounded computation -> response -> STM32 observes result** while the existing USB and OLED continue. Stop on unknown 3.3 V power capacity, bootstrapping ambiguity, invalid module firmware identity, unsatisfied Flash/SRAM/stack headroom, missing owner write consent or uncertain hardware ownership.
